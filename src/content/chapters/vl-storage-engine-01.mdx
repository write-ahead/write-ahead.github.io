### Naive log storage 

lets imagine a naive log storage , we will call it naive-log 

the naive-log would not be a strawamn, otherwise every solution the real victoria log gives for 
the naive-log problem would feel manufactured.

the naive-log would be something which could exist in real life as well as a solution for tiny scale logging.
This way we would really get to know the limitation of naive-log storage and how victoria logs solves it.

consider the following code for the naive-log

```go
// Append: O(1) amortized. Just bytes on the end of a file.
func Append(f *os.File, fields map[string]string) error {
	b, _ := json.Marshal(fields)
	_, err := f.Write(append(b, '\n'))
	return err
}

// Query: read the WHOLE file, parse EVERY line, filter in memory.
func Scan(path string, min, max time.Time, match map[string]string) ([]map[string]string, error) {
	f, _ := os.Open(path)
	defer f.Close()
	var out []map[string]string
	sc := bufio.NewScanner(f)
	for sc.Scan() {                              // (1) no skipping — reads every byte
		var row map[string]string
		json.Unmarshal(sc.Bytes(), &row)        // (2) parses every field to check one
		t, _ := time.Parse(time.RFC3339, row["_time"])
		if t.Before(min) || t.After(max) {
			continue
		}
		ok := true
		for k, v := range match {
			if row[k] != v {                    // (3) compares after full parse — no value index
				ok = false
				break
			}
		}
		if ok {
			out = append(out, row)
		}
	}
	return out, sc.Err()
}
```


the log comes in and is simply appended to the storage file on the disk.

and when we need to query for anything we need to scan the whole file because there is no index which could provide a sublinear path to the thing being searched for

### Limitation of naive-log 

Lets address the limitations of naive-log 

#### 1. No ordering 
when queried for some logs the matches could be anywhere in the file, no sorting no ordering, so not even binary search could be done.

#### 2. No grouping 
every line tested individually, no "these belong to streamx" kind of grouping 

#### 3. Row oriented 
must parse all fields of every line to read one 

#### 4. No value index within a field
even per column, token/substring search reads all the values 

### 5. Unbounded Growth
Append only means deleting old data = rewriting the whole fil( you can't punch a hole in the middle). Retention by age is impossible without a full rewrite.

#### 6. No compression 
Logs are wildly repetitive, but opaque JSONL only compresses generically and gzipping the file destroys random access to read line N you decompress from the start).

### What are we going to do in this blog entry 
we are not going to see how VictoriaLogs addresses the problems of naive-log. The first step would be 
what the log row is and where does it belong.

we can't start building optimizations like index and others over simple append only log.
So the first real move isn't an index, its imposing structure at the front door.

At ingest time VictoriaLogs parses the log into typed fields, separates the fields that identify the source ( the stream fields), computes a streamID from them,
and buffers the row in the column friendly shape.

This is the honest framing of this post: before you can be fast, you have to decide what you're storing. The naive store answers this question as "a line of text"; VictoriaLogs answers "a typed row that already knows its stream."
Every later rung — sorting, columns, bloom, the inverted index — is only possible because that decision was made at the door.

### Properties of a log workload 
it would be beneficial to discuss the properties of the log workload at this point.

because every good log storage engine would exploit these properties 

#### 1. Write pattern
the first property is this that logs are by nature appendonly, they are not updated in place, just write-once and then query.

#### 2. Volume 
They have an enormous volume (GB/TB per day), each row is individually cheap/low value.

#### 3. Time 
Logs roughly arrive in the time order, but you can never assume exactly.
when a log line shows up at the ingestion endpoint, its _time is usually close to "now" and usually later than the line before it.
But "usually" is not "always," and the gap between those two words is what forces a real design decision.

#### 4. Repetition 
The log data is massively repetitive - level , service , host , k8s  labels repeat

#### 5. Query-shape 
The most frequent queries include 
time range , a few field filters  and free text search 

#### 6 Retention 
We don't need to retain the logs data for long periods of times as we do in other main stream databases.

### The steelman — the obvious fixes, and why each fails
A sharp reader will shout four fixes at the screen. Answer them, and each answer is the motivation for a specific VL design choice.

#### 1. Just add an index on every field
This is roughly what Elasticsearch does — and why it needs ~30× the RAM and ~15× the disk of VictoriaLogs. It ignores workload: logs are too high-volume and too cheap-per-row to afford a precise index on everything. 

#### 2. Just keep the file sorted by time 
you destroy the O(1) append that made the naive store attractive in the first place
And one sort order still can't serve stream + field queries. VL's answer (the LSM move): never re-sort a giant file — write many small, immutable, already-sorted parts, and merge them in the background.

#### 3. Just use one file per day
Half-right — that's partitioning, and VL does exactly this for retention. But it only bounds coarse time and deletion; within a day you still full-scan. Necessary, not sufficient. 

#### 4. Just gzip the file.
Kills random access — to read line N you decompress from byte 0. Compression has to be per block so you decompress only what you read. 

### VictoriaLogs ingestion 
The entire ingest layer exists to melt ~10 different wire formats down into one neutral shape — (timestamp, []Field) — and hand it across a two-method interface. Everything protocol-specific dies at that boundary.

That's why VL can speak Loki, Elasticsearch, OTel, syslog, journald, Datadog, Splunk, jsonline, and its native protocol without the storage engine ever growing a protocol-specific branch.

### Buffering — one processor, one cart, three triggers

`AddRow` does **not** store a row. A single request can carry thousands of lines, and writing each one to storage individually would recreate the naive store's tiny-write problem. So for each request the handler opens **one processor** owning **one reusable buffer** — call it the cart — and every line is dropped into that same cart until something decides to wheel it away.

The cart isn't freshly allocated; it's borrowed from a pool (`GetLogRows`), already labelled with this request's `CommonParams` so it knows how to shape each line without being re-told. At terabytes a day, make-and-discard would bury the garbage collector; reuse is the Post-0 "cheap per row" economics showing up in code.

#### AddRow, per line (`common_params.go:253`)

```go
lmp.mu.Lock(); defer lmp.mu.Unlock()                     // claim the cart
lmp.unflushedRows++; lmp.unflushedBytes += EstimatedJSONRowLen(fields)  // tally (for metrics)
if len(fields) > *MaxFieldsPerLine { drop + warn; return }   // guard: default 1000
lmp.lr.MustAdd(cp.TenantID, timestamp, fields, streamFieldsLen)   // into the cart → streamID + layout
if lmp.cp.Debug { render; ResetKeepSettings; return }    // dry-run: show, don't keep
if lmp.lr.NeedFlush() { lmp.flushLocked() }              // size trigger
```

The lock exists because a **background timer goroutine** can also reach for the same cart (next). The two counters are for **metrics** (`vl_rows_ingested_total` and friends) — the "is the cart full?" decision is a separate measurement the cart keeps on *itself* (`NeedFlush`: more than 1.75 MB of bytes, or more than ~20,971 rows).

Inside `MustAdd`, which door is taken is a plain if / else-if / else:

- **Door A — positional** (`streamFieldsLen >= 0`): the first `N` fields *are* the stream fields. OpenTelemetry and Loki, where the protocol already groups identity fields up front.
- **Door B — configured names**: walk all fields, keep the ones whose name is in the request's `_stream_fields` list. jsonline, Elasticsearch, Datadog, Splunk — this is the `_stream_fields=service` route.
- **Door C — embedded `_stream`**: the row already carries a `{service="api"}` label (re-importing VL's own exported logs); parse it back. No label either → the single empty stream `{}`.
- **The native door** (`MustAddInsertRow`): in a cluster the id was computed once at the edge and shipped precomputed, so this door skips the recipe entirely.

Then all of them converge:

```go
bb.B = st.MarshalCanonical(bb.B)   // sort tags → canonical bytes (order-independent)
sid.tenantID = tenantID
sid.id = hash128(bb.B)             // the 128-bit hash
```

<MarginNote>
  <b>A stream field is identity <i>and</i> stored.</b> Doors A and B only <em>copy</em> a field into the tags — they never remove it from the row. So <code>service=api</code> becomes part of the id <b>and</b> stays a stored column. Only a client-sent <code>_stream</code>/<code>_stream_id</code> gets blanked, because VictoriaLogs regenerates those itself. And only the stream fields are hashed — put a high-cardinality field in there and you get a stream per line.
</MarginNote>

### The gate and the layout

The streamID done, the row reaches `mustAddInternal` (`log_rows.go:428`) — the last stop in this post. It does two jobs: check the row is allowed in, then lay it into the cart in a deliberately odd shape.

#### The gate — three limits

Before that, each field runs a quick filter — empty values are dropped (empty = missing), `_time` is dropped (it lives in the `timestamps` column), `_stream`/`_stream_id` are rejected, and `_msg` is canonicalized to the empty name. And one guarantee: every stored row ends up with a `_msg`, falling back to `-defaultMsgValue` if the line had none.

Be precise about the limits of what we've built: this is **not yet columnar** (each row's fields are still grouped in its window), and **not yet sorted**. The sort by `(streamID, timestamp)`, the transpose into real columns, and the freeze into an immutable part all happen past the socket — and that's where Post 2 opens.

### What you now know

<ol class="steps">
  <li>Before you can be fast you must decide <b>what you store</b>. The naive store says "a line of text"; VictoriaLogs says "a typed row that already knows its stream" — and it decides this at the <b>front door</b>.</li>
  <li>~10 protocols funnel into one neutral shape, <code>(timestamp, []Field)</code>, via three transformations — <b>flatten</b>, <b>extract <code>_time</code></b>, <b>rename <code>_msg</code></b> — all driven by the per-request <span class="ink-accent">CommonParams</span>.</li>
  <li>Rows pile into <b>one pooled buffer</b> per request, flushed by size, a ~1s timer, or close — and pushed through a <b>two-method socket</b> that is the entire single-node-vs-cluster fork.</li>
  <li>The <span class="ink-accent">streamID</span> is one recipe reached by <b>four doors</b>; a stream field is <b>identity and stored</b>, and only stream fields are hashed.</li>
  <li>In the buffer, a row is laid out as <b>parallel columns</b>, not a bundle, with repeated field values <b>stored once</b> — a shape chosen to make the next post's sort and columns cheap.</li>
</ol>
