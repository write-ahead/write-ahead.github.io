In the last post we watched a log line come in the front door: parsed into typed fields, stamped with a `streamID`, and dropped into an in-memory buffer. That is where we stopped — and it is worth being honest about how little we have so far.

The buffer holds the rows **in the order they arrived**. Nothing more. The structure we worked so hard to compute (the streamID on every row) is sitting there unused, like luggage tags on bags still piled by the door.

Three things about this buffer carry the whole post:

- It has structure we computed — a `streamID` per row — but it **has not used that structure yet**. The rows are laid out by arrival, not by anything meaningful.
- It is still in RAM, and it is still **growing**. More rows keep landing in it.
- It is **not a file**. Nothing is on disk, nothing is searchable, nothing another process could ever read.

Post 2 has one job: turn *this* into something on disk that you can actually search, and later, merge.

### The naive flush

The obvious move — the one you would write first — is to wait until the buffer fills up and then **spill it to a file exactly as it sits**. Arrival order, one row after another. New rows keep appending to that same file over time.

This is the honest baseline. It genuinely works. It is `cat buffer >> file`, forever. So instead of hand-waving that it is "bad," let us actually try to *use* this file — and watch exactly where it breaks. Each crack has a name, and each name is one of the three moves that make up the rest of this post.

A sorted array is the cheapest index there is: binary-search to the first match, walk forward until the key changes, stop. Arrival order throws all of that away. So the first forced move is simple to state: **sort the rows before you write them.**

The interesting question is *sort by what.*

#### Sort by (streamID, timestamp) — streamID first

Your instinct for a logging system is probably "sort by time." VictoriaLogs does not. It sorts **primary by `streamID`, secondary by `timestamp`** — the stream is the first key, time only breaks ties within a stream.

<MarginNote>
The sort key lives in <code>logRows.Less</code> — compare streamIDs first, fall back to timestamp only when they are equal. Everything in this post follows from that one ordering choice.
</MarginNote>

Sorting streamID-first makes **each stream a single contiguous run**. That is the layout you want for three different reasons at once: a stream query seeks straight to its run; a stream's wildly repetitive rows now sit next to each other (which is what sets up compression two posts from now); and one stream can be addressed without disturbing any other.

There is an honest objection to answer here, because a sharp reader is already raising it:

> "If `streamID` is the primary key, haven't you just **given up** fast time-range queries across all streams?"

Partly, yes — you can no longer binary-search the whole file by time. Two things pay that back, and they are worth naming now even though the machinery lands later:

1. **Ingest is roughly time-ordered** (that was workload property ③ from the last post). So within one flush, each stream's run is already time-*local* — it does not smear across the whole day.
2. The next move attaches a **min/max timestamp to every block**. A time-range query reads those headers and *skips* whole blocks whose range cannot match — a coarse time index that survives the streamID-first order. (And the partition itself is bounded to a day, but that is Post 8.)

So the choice is not "stream instead of time." It is "**stream as the sort key, time as cheap per-block skip metadata.**" Hold onto that framing — it is the reason the on-disk layout looks the way it does.

### Crack #2 — one giant run has no seekable sub-unit

Say we sorted the entire buffer into one long sorted blob. Better! But it is still *one object*. To read stream `S_api` you open the blob and scan to its run. To skip `S_api` by time you would have to read it anyway. There is no unit smaller than "the whole thing" to seek to, to skip, or — later — to compress on its own.

So we cut the sorted run into **blocks**.

<Figure caption="Cutting the sorted run into blocks. A block is the atom of storage: one stream's rows, in time order, with a tiny header carrying the streamID, the min/max timestamp, and a row count. Because the header describes the block, a query can reject a whole block — wrong stream, or a time range that cannot match — by reading a few bytes, never opening the rows. That skip is the first sublinear path in the entire series.">

Both failures have one root cause: **the file is still changing.** Maintaining sort order under a stream of out-of-order appends means mid-file inserts — O(n) per row, which throws away the cheap ingest from Post 1. And a layout that moves under a reader forces a lock on every read, or risks a torn one.

So the flush does not produce a file you keep editing. It produces a **write-once, never-modified unit: a part.** The instant a part is sealed, its sort order and block boundaries are frozen. Readers need no locks, because nothing inside a part ever changes again.

The trade is deliberate. Inside a part, everything is sorted. *Across* parts, nothing is — a 09:01 row in part 2 might be older than a 09:03 row in part 0. We accept that on purpose, because immutability is the precondition that lets the next post **merge parts safely in the background** without ever locking a reader. We are only planting that seed here; Post 3 grows it.

### Inside the flush: the two sorts

We said a part is built in three moves — sort, cut, freeze. The rest of this chapter opens the box on the first one. It turns out to be *two* sorts, not one, and the reason the whole thing stays fast even for fat log rows is worth watching up close.

All of it lives at the top of one function:

```go
func (mp *inmemoryPart) mustInitFromRows(lr *logRows) {
	mp.reset()
	sort.Sort(lr)            // sort #1 — reorder whole rows by (streamID, timestamp)
	lr.sortFieldsInRows()    // sort #2 — reorder fields within each row by name
	// ... cut the sorted rows into blocks (next section) ...
}
```

<MarginNote>
The <code>lr</code> handed in here is a pile of rows aggregated from many ingest requests and buffered for about a second before the flush. That buffer is its own story — we open it in the next chapter. For now it is just "a full buffer, in arrival order."
</MarginNote>

#### The buffer is a structure-of-arrays

A log row can be fat — a hundred fields. If a row were one contiguous record, sorting a million of them would mean shoving a lot of bytes around. VictoriaLogs sidesteps that by never storing a row as a contiguous thing at all. The buffer is a set of **parallel arrays** — a structure-of-arrays — tied together by position.

#### Sort #1 — reorder the rows

`logRows` implements Go's `sort.Interface`, so `sort.Sort` can reorder it. The comparison is two-tiered:

```go
func (lr *logRows) Less(i, j int) bool {
	a, b := &lr.streamIDs[i], &lr.streamIDs[j]
	if !a.equal(b) {
		return a.less(b)                       // primary key: streamID
	}
	return lr.timestamps[i] < lr.timestamps[j]    // tie-break: timestamp
}
```

#### The trick — `Swap` moves pointers, not data

Here is why sorting a buffer of fat rows is not expensive. Look at what `Swap` actually exchanges:

```go
func (lr *logRows) Swap(i, j int) {
	lr.streamIDs[i],  lr.streamIDs[j]  = lr.streamIDs[j],  lr.streamIDs[i]   // ~24 bytes
	lr.timestamps[i], lr.timestamps[j] = lr.timestamps[j], lr.timestamps[i]  //   8 bytes
	lr.rows[i],       lr.rows[j]       = lr.rows[j],       lr.rows[i]         //  24 bytes (a slice header)
}
```

`rows[i]` is a **slice header** — a pointer, a length, a capacity. Swapping `rows[i]` with `rows[j]` just swaps *which fieldsBuf window* each row points at. It does not move a single field, and it never touches the arena.

One invariant keeps this correct: the three arrays are only meaningful *together*, so `Swap` moves all three in lockstep. ### Cutting the sorted rows into blocks

The sort is done; move two is to **cut**. A single loop walks the sorted rows top to bottom, dropping each into a box, and tapes the box shut whenever a block should end. It keeps four scraps of state: `bsw` (the sealer that bakes a box into a finished block — its internals are Post 4), `trs` (the box being filled), `sidPrev` (the box's stream), and a running size tally.

```go
trs := getTmpRows()
var sidPrev *streamID
blockSize := uint64(0)                 // uncompressedBlockSizeBytes

for i := range timestamps {
	streamID := &streamIDs[i]
	if sidPrev == nil {
		sidPrev = streamID             // first row: label the first box
	}
	if blockSize >= maxUncompressedBlockSize || !streamID.equal(sidPrev) {
		bsw.MustWriteRows(sidPrev, trs.timestamps, trs.rows)   // ← seal the current box
		trs.reset()
		sidPrev = streamID
		blockSize = 0
	}
	trs.timestamps = append(trs.timestamps, timestamps[i])     // drop this row in
	trs.rows = append(trs.rows, rows[i])
	blockSize += uint64(EstimatedJSONRowLen(rows[i]))
}
bsw.MustWriteRows(sidPrev, trs.timestamps, trs.rows)           // ← seal the final box
```

Everything hinges on that one `if`. Tape the box shut and start a fresh one when **either** the stream changes (so a block is always exactly one stream) **or** the box reaches 2 MiB (`maxUncompressedBlockSize`, so even a giant stream is chopped into bounded blocks). Because the rows are sorted streamID-first, each stream's rows are already contiguous, so "stream changed" fires cleanly at the boundary between one run and the next.

Two subtleties worth naming. First, **a box gets sealed in two places**: inside the loop, when the *next* row forces a cut — and once more *after* the loop, because the final box has no "next row" to trigger it. ### Freezing the part to disk

```go
func (mp *inmemoryPart) MustStoreToDisk(path string) {
	fs.MustMkdirFailIfExist(path)                      // 1. create the dir (must not exist)

	var psw filestream.ParallelStreamWriter
	psw.Add(".../timestamps.bin", &mp.timestamps)      // 2. pair every buffer with its file
	psw.Add(".../index.bin",      &mp.index)
	// ... all the others, _msg to message_*, the rest to bloom.bin0 / values.bin0 ...
	psw.Run()                                          // 3. write them all, in parallel

	mp.ph.mustWriteMetadata(path)                      // 4. write metadata.json LAST

	fs.MustSyncPathAndParentDir(path)                  // 5. fsync the dir, for durability
}
```

Each step earns its place. The directory is created with `MustMkdirFailIfExist` — it **panics if the directory already exists**, which is immutability made physical: a part directory is written once and never reopened. Each in-memory buffer is paired with its filename (the 1:1 map from the previous section) and all the files are written **in parallel**, because on networked storage serial writes are slow. Then — and this ordering is the whole durability story — `metadata.json` is written **last**, and the directory is fsynced.

### What you now know

<ol class="steps">
  <li>Post 1 ends with a buffer of typed rows in **arrival order**; this post turns it into an immutable part on disk, in three moves.</li>
  <li><strong>Sort</strong> by <code>(streamID, timestamp)</code> — really <code>(tenantID, streamHash, timestamp)</code> — so each stream becomes one contiguous, time-ordered run. The sort is cheap because the buffer is a structure-of-arrays: swapping rows moves tiny headers, never the field bytes. A second sort puts each row's fields in canonical name order.</li>
  <li><strong>Cut</strong> the sorted rows into <strong>blocks</strong>: one loop, a fresh block whenever the stream changes or the box hits 2 MiB, with a mandatory seal for the final box.</li>
  <li>Each block is sealed into the part; <code>Finalize</code> writes the <strong>part header</strong> — eight fields, a <em>time</em> range (no streamID range — that's in the per-block index), persisted as <code>metadata.json</code>.</li>
  <li>A part is a <strong>directory</strong> of <code>metadata.json</code> plus <code>.bin</code> files; the in-memory part has one buffer per file.</li>
  <li><strong>Freeze</strong>: <code>MustStoreToDisk</code> writes those buffers out in parallel, <code>metadata.json</code> last, then fsyncs — an atomic, durable, write-once part.</li>
  <li><strong>And it checks out on disk</strong>: 5 rows → 2 blocks (one per stream), <code>FormatVersion 3</code>, one bloom/values shard (<code>bloom.bin0</code>), a timestamp range and no streamID range — exactly as claimed.</li>
</ol>

The row is now a sorted, immutable, file-backed part — the unit every later post operates on. But each flush makes a *new* part, so a busy server piles up thousands of tiny ones. The next chapter is the engine that tames them: the in-memory buffer and the background **merge** that folds many small parts into fewer big ones — the heart of the LSM design.
